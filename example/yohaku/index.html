==历史怎么走==

从对象和指针，走到分支与合并。

talk-in-slides公开教学示例 · 合成图解
这份示例延续“用对象和指针理解 Git”的教学主线。所有节点都是合成标识，不对应任何真实项目。这是通用协作原理，不是 Gitflow 的 release/develop 分支规范。

一 · 对象

四种对象，各管一件事

01 · 文件内容

blob

保存内容，不保存文件名。

02 · 目录结构

tree

记录名字、模式与对象引用。

03 · 一次快照

commit

关联根 tree、父提交与元数据。

04 · 附注标签

tag

保存目标、说明与打标者信息。

概念依据：Pro Git · Git Objects；轻量标签只是引用，不创建 tag 对象。

逐一揭示四类对象。commit 的父提交可为零个、一个或多个；根提交没有父提交。附注标签可以带签名，签名不是必需条件。

快照

提交指向快照，差异按需计算

文件名写在 tree 里；内容没有变化，就能复用同一个 blob。

关系示意，省略父提交与元数据；依据：Pro Git · Git Objects。

图上的连线表示对象引用。Git 的逻辑模型保存快照，展示 diff 时比较快照；底层打包可能采用差量压缩。不要把逻辑快照和磁盘上完整复制混为一谈。

二 · 指针

新建分支，只增加一个指针

两个分支可以指向同一次提交。
分支名不同，文件不必复制一份。

git switch -c feature

正常附着状态下，HEAD 指向当前分支。

A、B 为合成提交标识；依据：Pro Git · Branches in a Nutshell。

先给出提交 A、B，再让 main 指向 B；执行 switch -c 创建 feature 并切换，HEAD 于是指向 feature。detached HEAD 是例外，不在本页展开。

三 · 整合

分叉之后，merge 保留两条来路

M 同时引用 C 和 D，已有提交保持不变。

连线表示历史关系，时间从左到右；演示非 fast-forward 的双分支合并。

这里历史已经分叉。合并产生两个父提交的新 commit M，main 前进到 M，feature 仍指向 D。若目标能直接快进，默认 merge 不必创建合并提交；不能概括成每次 merge 都产生新节点。

重放

rebase 重放改动，形成新的提交

D 的改动应用到 C 之后，得到 D′；父提交改变，标识随之改变。

关系为合成示意；原 D 仍可能由 reflog 等引用保留，不会因重放立即消失。

在 feature 上执行 git rebase main。示例假设改动成功重放且不是空提交。旧 D 没有瞬间移动到新位置；新 D′ 有不同的父提交。不要擅自改写其他人正在依赖的共享历史。

协作选择

先约定历史，再选择整合方式

需要保留什么 可选方式 先检查什么
分支整合的来路 merge 是否已分叉、是否需要合并节点
线性的个人提交 rebase 是否有人依赖这段历史

两条路径可能得到相同文件内容；冲突处理不同，结果也可能不同。

依据：Pro Git · Basic Branching and Merging / Rebasing。

按行说明适用条件。merge 和 rebase 并不保证任何情况下都得到相同 tree。实际团队还会使用 squash 等策略，应在评审和发布约定中明确，不靠个人习惯随意切换。
